# A gamepad is player 1, with its Start and Select

2026-11-15 · owner: "Arregla fbneo". Found while laying out the touch pad (engine-specs
`RECORD/2026-11-15.virtual-touch-gamepad.WIP.md`): a gamepad's Start and Select did nothing here.

**Status:** being implemented (the owner asked for the fix).

## Found (FBNeo @ `d7179fef`, SDL2 burner)

It is worse than Start and Select: **today a gamepad plays player 2, not player 1.**

- The SDK starts FBNeo as `callMain([driver])`, without `-joy` (`src/fbneo.sdk.ts`).
- Without `-joy` (`usejoy = 0`), `GameInpAutoOne` (`src/burner/gami.cpp`) binds **player 1 to the
  keyboard only** (`nPlayerDefaultControls[0] = 0` → `GamcAnalogKey` + `GamcMisc` +
  `GamcPlayer(…, -1)`) and **player 2 to joystick 0** (`GamcPlayer(…, 0)`). Player 2's Start and Coin
  come from `GamcMisc`, which knows keys only (`2` and `6`). So the first pad moves player 2, and its
  Start / Select reach nothing.
- With `-joy`, `MapJoystick` (`src/burner/sdl/input_sdl2.cpp`) binds player N to joystick N-1 through
  SDL's game-controller layer: directions (stick, and the d-pad via `SDLinpDPad`), fire 1–6 = A B X Y
  LB RB, **Coin = Back (Select), Start = Start**. On Emscripten SDL2's default "Standard Gamepad"
  mapping that is buttons 0–5, 8 and 9 — exactly what the touch pad's Neo Geo layout presses.
- FBNeo binds each input to **one** device: with `-joy` player 1 has no keyboard. And with `-joy` but
  no pad, player 1 would be bound to a joystick that is not there — nothing would work.
- FBNeo looks for pads **once**, in `SDLinpInit` (no hot-plug). That is true today too.

## Plan

1. **SDK** (`src/fbneo.sdk.ts`): pass `-joy` when a gamepad is connected at start —
   `navigator.getGamepads()` holds one (a browser lists a pad once a button on it was pressed on the
   page; the touch pad is listed as soon as the host exposes it). Then player 1 is the first pad and
   player 2 the second, each with Start and Select. With no pad: as today, player 1 on the keyboard.
   The choice is logged (`[fbneo] player 1: gamepad` / `keyboard`) and readable as
   `play.controller` (`'gamepad' | 'keyboard'`), so an app can tell the player.
2. **What this costs, accepted**: with a pad at start, player 1's keys (arrows, Z X C V, 1, 5) do not
   play — FBNeo's one-device rule. The app's own keys (Escape → pause menu) are JS and keep working.
   A pad first touched after the game started is still not seen (FBNeo's start-up enumeration).
3. **Docs**: README (controls), CORE.md (the input binding and why).
4. **Tests**: the argument choice as a pure function (`fbneoArgs(driver, gamepads)`), unit-tested.
5. **Not now** — a build patch: `MapJoystick` has no case for `p1 select` (the AES pad's Select),
   so in AES mode the pad's Select presses Coin, which the AES ignores. Few AES games use Select;
   adding a `select` case is a source patch and a rebuild, its own change.

## Verify

- `make test` (type-check + tests).
- In a browser, with the released `fbneo.wasm` and the rebuilt SDK, a set FBNeo can run without
  copyrighted data, if one is at hand: a standard gamepad exposed before start inserts a coin with
  Select and starts with Start.

## Extension (2026-11-15 13:55) — the app's menus by touch

Found with the touch pad on a phone: the pad hides while a menu is open, and the menu is tapped
(engine-specs UX.md, "Touch"). The pause menu works by touch (its items take a click), but the
**suspend-point screen** has actions that only a gamepad button reaches:

- B (back / exit / cancel the slot choice) — no on-screen element does it;
- Y ("guardar en un hueco" on the unsaved point, "opciones" on a saved one) — none either, and a tap
  on a card plays it, so a card cannot even be focused by touch;
- the options sheet has no way back but B;
- the hints show gamepad glyphs (A / B / Y) on a phone.

Plan (same change in blastem-wasm's app, which is this app on BlastEm's SDK):

1. **Hints become buttons**: `hints([[glyph, label, action]])` draws a `<button data-act>` when the
   hint has an action; a tap runs that action through the same handler as the gamepad (A → accept,
   B → back, Y → more). Hints without an action (←→ elegir, A elegir) are gamepad-only.
2. **Long-press on a card** (500 ms, a finger that stays put) focuses that card and runs `more` —
   Y's job — and the click that follows the lift is dropped.
3. **The sheet gets its hint**: "B volver".
4. **On touch screens** (`pointer: coarse`): hint buttons get a 44 px target and no glyph; the
   gamepad-only hints are hidden; the overlay has no text selection, callout or context menu.

Verify end to end (Gridlee, phone emulation): leave with a suspend point, come back to the points
screen; long-press the unsaved point → the slot choice; "cancelar" → back; "salir" → the "¿Volver al
lanzador?" question.

## Walkthrough (2026-11-15 14:05) — the app's menus by touch

- `src/app/app.js`: `hints()` draws `<button class="hint" data-act>` for hints with an action
  (points: jugar / guardar aquí → accept, guardar en un hueco / opciones → more, salir / volver /
  cancelar → back; pause: continuar → back; the sheet gains "volver" → back); the gamepad handler
  became `onAction`, shared by `host.input` and the hint buttons; a long press (500 ms, ≤ 12 px of
  drift, not a mouse) on a card focuses it and runs `more`, and the click after the lift is dropped;
  no context menu on the overlay.
- `src/app/app.css`: hint buttons; on `pointer: coarse` 44 px pills without glyphs, gamepad-only
  hints hidden; no selection / callout on the overlay's buttons.

Verified: `make test` 24 / 24; end to end on Gridlee as an iPhone 13 — after "Volver al lanzador"
from the pause menu (touch pad's pause button, then the item), mounting again shows the points
screen with **jugar · guardar en un hueco · salir** as 44 px buttons and no glyphs, the touch pad
hidden; a long press on the unsaved point saved it into slot 1 ("Guardado en el hueco 1": the
app's Y with a free slot); "salir" → "¿Volver al lanzador?".
